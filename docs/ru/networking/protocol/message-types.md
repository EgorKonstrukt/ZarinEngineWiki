# Типы геймплейных сообщений (NET_*)

Проводные идентификаторы геймплейного неткода: перечисление `MessageType` в `core/network/protocol.py:80-91`. Значения 100–111; коллаборация занимает типы 1–55 и 210–212.

## Формат фрейма

`make_msg(msg_type, data)` упаковывает msgpack `{"t": int(msg_type), "d": dict}` и добавляет префикс длины `">I"` (big-endian uint32); `parse_msg` — обратное преобразование, `pack_frame` / `unpack_frame` — алиасы. `FRAME_HEADER_SIZE = 4`, `MAX_MESSAGE_SIZE = 4 МиБ` — слишком большие пакеты кидают `ValueError` вместо отправки. Крупные передачи идут через `split_chunks` (`CHUNK`), а не одним фреймом.

## Приём и ретрансляция сервером

Каждый клиентский фрейм проходит `GameServer._client_loop`: в локальную очередь с меткой `_sender` попадают только разрешённые типы (`server.py:232-247`). Из них другим пирам рассылаются только transform/rigidbody/animator/variables/RPC/snapshot (`server.py:248-263`). Запросы спавна, смены владельца, деспавны и ready-флаги потребляет `NetworkManager`, они не ретранслируются. Смежные типы рукопожатия: первый фрейм обязан быть `JOIN`, ответ — `JOINED`; отключения рассылаются как `LEAVE`; `PING` получает `PONG` сразу и в очередь не попадает.

## Таблица типов

| Тип | Значение | Назначение (одной строкой) | Кто шлёт / ретрансляция |
|---|---|---|---|
| `NET_SPAWN` | 100 | Сервер объявляет новую сущность `{net_id, owner_id, prefab_id, entity}` | Сервер `broadcast` (опоздавшему — `send_to` через `_sync_new_peer`); клиенты применяют в `_handle_spawn` |
| `NET_DESPAWN` | 101 | Удаление сущности `{net_id}` | Сервер рассылает, клиент шлёт как запрос серверу; сервер принимает, но **не** ретранслирует |
| `NET_SPAWN_REQUEST` | 102 | Клиент просит сервер заспавнить `{prefab_id, entity, requester, pos?, rot?}` | Только клиент → серверу; обрабатывает лишь сервер (`_handle_spawn_request`), не ретранслируется |
| `NET_RPC` | 103 | Вызов: плагинный `{"rpc", "payload"}` или компонентный `{"net_id", "method", "args", "rpc_type", "target?"}` | В обе стороны; **ретранслируется** другим пирам; см. RPC-справочник |
| `NET_TRANSFORM` | 104 | Состояние трансформа `{net_id, t, seq, p?, r?, s?}` | Шлёт сторона-владелец; **ретранслируется**; применяется в `NetworkTransform.apply_snapshot` |
| `NET_RIGIDBODY` | 105 | Состояние физики `{net_id, t, seq, v?, w?}` | Шлёт владелец (из `on_fixed_update`); **ретранслируется**; применяется в `NetworkRigidbody.apply_snapshot` |
| `NET_ANIMATOR` | 106 | Состояние аниматора `{net_id, t, seq, clip?, time?, speed?, playing?, params?, trigger?}` | Шлёт владелец; **ретранслируется**; применяется в `NetworkAnimator.apply_snapshot` |
| `NET_OWNER_CHANGE` | 107 | Смена владельца; клиент шлёт `{requester}`, сервер рассылает `{net_id, owner_id}` | Клиент → сервер → `broadcast`; сервер принимает, но авторетрансляции нет |
| `NET_VARIABLES` | 108 | Синхронизируемые переменные `{net_id, vars, t, seq}` (старый ключ `data` тоже читается) | Шлёт владелец; **ретранслируется**; применяется в `NetworkVariables.apply_snapshot` либо через общий `setattr`-фолбэк |
| `NET_READY` | 109 | Зарезервированный флаг готовности | Сервер принимает и кладёт в очередь, **не** ретранслирует, встроенной ветки в `NetworkManager` нет |
| `NET_KICK` | 110 | Принудительное отключение `{reason}`, напр. `server_full` при переполнении | Сервер → одному пиру, затем закрывает сокет; `Transport.connect` возвращает `False`, увидев его |
| `NET_SNAPSHOT` | 111 | Зарезервированный канал снимка всего мира | Принимается и **ретранслируется** как каналы состояния; встроенных отправителей/получателей нет — под пользовательские данные |
