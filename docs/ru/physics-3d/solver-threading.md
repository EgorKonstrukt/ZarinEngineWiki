# Солвер и многопоточность

Режимы выполнения:

- `single` — `PhysicsScene` + солвер в процессе игры. Минимальная задержка, требуется для `CharacterController`.
- `multi_threaded` (по умолчанию) — демон-`multiprocessing.Process` владеет солвером; очереди команд/результатов плюс общие буферы (`SharedPhysicsBuffer`, `SoftSharedBuffer`) несут трансформы, скорости, силы и события столкновений.
- `per_layer_process` — процессы солвера spawning по требованию на слой коллизий.

Фоновый шаг:

1. Висящие команды `step` сливаются в один `dt` (нет спирали смерти на фризах).
2. Воркер применяет телепорты (`set_body_transform`) или скорости/силы/моменты из общей памяти.
3. Работает `solver.step_simulation(dt)`; у 2D-тел обнуляются внеплоскостные скорости.
4. Позиции, повороты и скорости пишутся назад с bump версии; вершины soft-body, центр масс и скорости — в soft-буфер.
5. События столкновений маппят id тел солвера на id сущностей и уходят в очередь результатов для диспатча в скрипты.

Флаги тел в общей памяти: 1 = активно, 2 = грязная скорость, 4 = телепорт, 8 = 2D-тело. Внутрипроцессный путь повторяет тот же порядок без сериализации: регистрация → ECS-в-физику → шаг → ограничение 2D → физика-в-ECS → soft-синк → события.

Обвязка фиксированного шага: `Engine.tick_fixed_step` копит реальное время относительно `_fixed_dt = 0.02`, выполняет `pre_step` плагинов, `scene.fixed_update`, затем шаг физики — скрипты видят стабильный `dt` в `on_fixed_update`.
